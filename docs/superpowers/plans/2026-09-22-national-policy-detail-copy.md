# 전국 교통 정책 11건 상세 채우기 계획

상태: 계획. 코드 없음. 승인 뒤 구현.
브랜치: `feature/national-policy-detail-copy` (origin/develop `a1e3d10` 기준)

## 왜

전국 교통 정책 11건(`travelmonth-104`~`114`)은 `structured_detail`이 비어 있어 상세 화면이 카드 문구 한 줄로 끝난다.
지역 정책(예: `dgtour-하동`)은 5개 섹션이 채워져 있다. 앱의 목적이 정책 사이트 유도이므로
**어떤 혜택인지 · 어떻게 받는지 · 어디로 가는지**를 상세에서 답해야 한다. 쓸모없는 텍스트는 넣지 않는다.

확정된 범위(2026-09-22 사용자 결정):
- 출처: 여행가는 달 교통 안내 페이지(`traffic.do`) 본문. 예외는 114 한 건(아래).
- 표기 위치: 정책 상세 화면. 카드 문구는 109 한 건만 손댄다.
- 대상: 전국 교통 11건만. 다른 수집원·지역 정책은 건드리지 않는다.

## 정체를 정확히 말하면

"수집원별 규칙"이 아니라 **핵심 제목(`core_traffic_title`)으로 찾는 정리된 문구 표 + 수집 시 파싱된 값(기간·URL·카드 문구)의 결합**이다.

| 재수집 때 자동으로 따라오는 것 | 따라오지 않는 것 |
|---|---|
| 기간(start/end, issue/usage), 공식 URL, 카드 문구 | 섹션 본문(사람이 정리한 문장) |

제목이 바뀐 카드는 표에서 빠져 일반 경로(혜택 원문 + 기간)로 떨어진다. 테스트가 이를 잡는다.

## 코드 이음매 (확인됨)

- `policy_semantic_mapping._MAPPERS`에 `traffic_benefit`이 없다 → `mapper_status="missing"`, 빈 상세.
- `promote_external_benefit_record()`가 `policy.structured_detail = mapping.structured_detail`을 쓴다(`policy_normalization.py:314, 382`).
- 상세 지문(`_detail_fingerprint_payload`)은 **레코드**만 본다. 매퍼를 추가해도 재수집에서 후보가 생기지 않는다 → 이미 공개된 11행은 **데이터 마이그레이션**으로 채운다(선례 `0032_dgtour_structured_detail.py`).
- 프런트는 변경 없음. `PolicyPages.tsx`가 `supportContent` 항목을 `title`별로 묶어 소제목 섹션으로 그린다.

### 프런트 계약 → 표 작성 규칙

1. `amount`는 넣지 않는다 (`structuredBenefitText(amount, description, value)` — amount가 description을 덮는다).
2. 소제목 = `supportContent` 항목의 `title`. 순서는 첫 등장 순.
3. 여러 단계(111 받는 방법)는 같은 `title`의 항목 여러 개. `\n`으로 잇지 않는다.
4. 기간 항목은 `type`을 `issue` / `usage` / `application` 중 하나로.
5. 표의 기간은 **표시용**이다. `policy.start_date/end_date`는 파서가 준 값만 쓴다(만료 판정이 바뀌면 안 된다).
6. `title`이 "혜택 적용 조건"인 항목은 프런트가 조건 섹션으로 옮긴다 — 의도할 때만 쓴다.
7. 카드 금액과 같은 문구로 끝나는 "…혜택" 항목은 프런트가 지운다(`isTopAmountDuplicate`) — 그런 문장을 만들지 않는다.

1. **107·113의 기간이 계획과 달랐다.** 레코드의 `periodEvidence`를 보니 9.15~11.26(107)·9.15~10.31(113)은 **예약 기간**이고 이용 기간은 따로 있다(107 10.1~11.30, 113 10.1~10.31). 표에 기간을 적지 않고 파서가 준 `periodEvidence`를 그대로 쓰므로 이 구분이 자동으로 지켜진다.
