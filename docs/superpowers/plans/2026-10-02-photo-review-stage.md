# 사진 검토 2단계: 수집은 후보만, 사람이 한 장을 확정

## 배경

1단계(`2026-10-01-photo-collection-criteria.md`)로 수집이 기준(공공누리 유형 · 시설 · 크기 · 도 일치 · 겹침)을 거치게 됐다.
그래도 고른 사진이 그 지역답지 않다. 시군 관광지 목록이 조회순·관광지만이라 절·계곡·마을이 먼저 나오고,
죽녹원 · 광한루원 · 하회마을 · 해인사 같은 대표 장소는 시군 목록에는 없고 키워드 검색에만 있다(10/1 실측).
정책 사진은 더하다. 정책 제목(디지털관광주민증 · 반값여행 · 숙박세일)과 이름이 맞는 관광지가 없어서
같은 시군의 다른 관광지가 겹치지 않게 하나씩 붙는다. 합천 반값여행 후보는 향교·서원 6곳이었다.

## 사용자 결정 (2026-10-01, 시안 v50·v51 승인)

- 수집은 후보만 넣는다. 관리자가 한 장을 확정해야 앱에 나간다.
- 시군 단위 · 후보 6장. 확정 전이거나 '모두 아님'이면 홈 시군 카드는 혜택 그림.
- 정책 사진도 같은 방식, 정책마다 후보 6장. 정책은 고르지 않으면 시군 사진을 그대로 쓴다.
- 대표 장소가 후보에 없으면 '이름으로 찾기'(관광공사 키워드 검색, 같은 기준, 음식점·숙박 제외).
- 배포 때 지금 들어가 있는 자동 사진은 검토 전으로 돌린다(화면에서 내린다).
- 같은 브랜치(`feature/photo-collection-criteria`)에서 한 PR. 4173 에서 사용자가 확인한 뒤 수정 사항을 받는다.

## 표 (Alembic `0047_photo_review`)

`photo_review_targets` - 검토할 대상 하나(시군 하나 또는 정책 하나)

| 칸 | 뜻 |
|---|---|
| `target_key` UNIQUE | `region:전남\|담양`, `region:전남\|`(도 전체), `policy:123` |
| `target_type` | `region` / `policy` |
| `sido`, `city` | 지역 대상의 키(`city ''` = 도 전체). 정책 대상은 정책의 지역을 복사해 둔다(시군 사진 물려받기용) |
| `policy_id` | 정책 대상만. `policies` 삭제 시 함께 지운다 |
| `status` | `pending` / `approved` / `none` |
| `approved_candidate_id` | 확정한 후보(외래키 없음 - 후보는 대상과 함께만 지워진다) |
| `decided_at`, `decided_by_user_id` | 마지막 결정 |

`photo_review_candidates` - 대상마다 후보 사진. `(target_id, image_url)` UNIQUE.
`source` 는 `collect`(수집) / `search`(이름으로 찾기, `search_keyword` 같이).
제목 · 관광공사 분류(`content_type_id`) · 원본/썸네일 주소 · 저작권 유형 · 크기 · 주소를 둔다.

앱은 '대상이 고른 후보'를 바로 읽는다(아래 '사진 보관 · 표 2개', 10/2 변경). 응답 쪽 해석 순서(정책 사진 → 시군 사진 →
혜택 그림)는 그대로다. `region_photos` / `policy_photos` 는 더 읽지도 쓰지도 않는다.

마이그레이션 데이터 단계: 기존 두 표의 `active` 사진 줄을 `review` 로 내린다(화면에서 빠진다). 후보로 옮기지는 않는다 -
수집 기준(0046) 이전에 고른 사진이라 저작권 유형을 몰라 확정할 수 없다(4173 확인 중 발견, 10/2). 대상과 후보는 수집이 만든다.
downgrade 는 새 표를 지우고 `review` → `active`.

## 수집 (`scripts/collect_photo_candidates.py`)

`backfill_region_photos.py` · `backfill_policy_photos.py` 를 대신한다(둘은 지운다 - 남겨 두면 검토 없이 사진을 내건다).
대상: 활성 정책과 수집 기록의 (도, 시군) + 도 전체 줄, 그리고 활성 정책 하나하나. 결정된 대상은 건드리지 않는다.
`pending` 대상은 `search` 를 뺀 후보가 6장이 되도록 채운다. 후보 줄은 그 시군(시군 코드)의 관광지(12) · 쇼핑(38) · 축제(15)를
조회순(arrange P)으로 받아 번갈아 섞고, 1단계 기준을 통과한 것만. 이미 다른 대상의 후보인 사진은 건너뛴다 - 시군을 먼저,
그다음 그 시군 정책을 채우므로 정책은 시군 후보 다음 사진을 받는다. 시군이 없는 대상은 도 전체 목록에서.

## 관리자 API (`/api/admin/photo-review/...`)

| | |
|---|---|
| `GET targets?unit=region\|policy&status=pending\|approved\|none\|all` | 목록 + 상태별 수 + 두 단위 검토 대기 합 |
| `GET targets/{id}` | 대상 + 후보 |
| `POST targets/{id}/approve` `{candidateId}` | 확정 - 원본을 받아 두고 앱 사진이 된다(못 받으면 502, 보관 위치가 없으면 503) |
| `POST targets/{id}/none` | 모두 아님(지역: 혜택 그림, 정책: 시군 사진 그대로) |
| `POST targets/{id}/reopen` | 다시 고르기 |
| `POST targets/{id}/more` | 관광공사에서 다음 6장 |
| `POST targets/{id}/search` `{keyword}` | 이름으로 찾아 후보에 더함(최대 6장) |

결정 셋은 `admin_audit_logs`(변경 이력)에 남긴다. `more` · `search` 는 관광공사 키가 꺼져 있으면 503.

## 후보 채우기 (시안 v52, 10/2 추가)

수집 스크립트가 크롤링 · 배포 어디에도 붙어 있지 않아(개발서버는 크롤링 스케줄러도 꺼져 있다) 배포 직후 목록이 비고, 새로 승인한
정책도 누가 스크립트를 돌려야 후보가 생겼다. 그래서 사진 검토 화면 머리 오른쪽에 '후보 채우기'를 둔다.

- `POST /api/admin/photo-review/collect` 가 같은 수집 함수(`collect_candidates`)를 서버 안에서 뒤에서 돌리고 바로 돌아온다
  (첫 수집은 몇 분 - Cloudflare 응답 제한 100초를 넘는다). 화면은 `GET` 으로 2초마다 진행을 묻는다.
- 대상 하나마다 저장한다 - 몇 분 동안 관리자 확정이 그 대상 잠금을 기다리지 않고, 끊겨도 받은 만큼 남는다. 스크립트도 같다.
- 한 번에 하나만(프로세스 안 잠금 - uvicorn 하나로 뜬다), 끝나면 변경 이력(`photo_review.collect`).
- 목록 응답에 `newTargets`(다음 수집이 넣을 대상) · `shortTargets`(후보가 모자란 대상)를 더해 버튼 아래에 보인다.

## 홈 배너 사진 출처 모으기 (시안 v53, 10/2 추가)

사진마다 출처를 적어야 하느냐는 질문에서 나왔다. 공공누리 · CC BY · CC BY-SA 는 출처 표시가 이용 조건이지만 사진 위마다 붙일 필요는 없고
그 매체에 맞는 합리적인 방식이면 된다. 홈 배너 장마다 붙던 '사진 · 작가 · 라이선스' 글자를 빼고 배너 아래 '사진 출처' 하나로 모은다 -
창에는 라이선스 본문 · 원본 링크까지 둔다(지금 글자에는 CC 가 요구하는 링크가 없었다). CC0 · 퍼블릭 도메인 2장은 의무는 없지만 같이 적는다.
로그인 사진(한 장)과 관광공사 사진(홈 시군 카드 줄 아래 한 번 · 정책 상세 사진 위)은 그대로 둔다.

## 사진 보관 · 표 2개 (10/2 추가)

'저장된 사진은 어디 있나', '사진 표가 너무 많지 않나'는 질문에서 나왔다. 확정 사진이 관광공사 주소였다 - 그쪽이 주소를 바꾸거나
지우면 확정한 사진이 조용히 사라진다. 그리고 확정이 같은 내용을 `region_photos` · `policy_photos` 에 한 번 더 베꼈다(표 4개).

- 확정할 때 그 한 장의 원본을 받아 `MEDIA_ROOT/photos/<해시 앞 2자>/<sha256>.<확장자>` 에 둔다(`app/services/photo_storage.py`).
  형식은 파일 첫 바이트로 가린다(오류 페이지를 200 으로 줘도 저장 안 함), 5MB 까지, 다시 인코딩 · 리사이즈하지 않는다
  (공공누리 제3유형 변경금지). 임시 파일에 쓰고 이름을 바꿔 반쯤 쓴 파일이 남지 않는다. 같은 사진은 한 파일.
- 못 받으면 확정하지 않는다(502). 다시 확정하면 받아 둔 파일을 그대로 쓴다.
- 후보 줄에 `stored_path` · `byte_size` · `content_type` 을 더했다(0047 을 고침 - 아직 배포 전). 앱은 확정 대상 → 그 후보 →
  받아 둔 파일만 읽는다. 표 두 개로 끝나고 `region_photos` · `policy_photos` 는 0047 이 `review` 로 내린 채 남는다
  (배포가 확인되면 지우는 마이그레이션을 따로).
- 내보내기는 백엔드 `/api/media`(`app/api/media.py`, StaticFiles + 1년 immutable 캐시). 응답은 상대 주소 `/api/media/...`,
  화면이 API 주소를 붙인다(`mediaUrl`).
- **9/17 보관 계획과 다른 점:** 그 계획은 Caddy `file_server` 로 내보내기로 했다. 백엔드가 내보낸다 - Caddy 는 지금처럼 `/api` 를
  백엔드로 넘기기만 하므로 Caddyfile · 로컬 4173 설정을 바꾸지 않아도 되고, 볼륨도 백엔드 하나에만 붙는다. 사진 수가 백여 장이라
  파이썬이 내보내도 부담이 없다. 많아지면 Caddy 로 옮긴다(주소는 그대로).
- 볼륨 `travelhunter-media` 와 `MEDIA_ROOT`(기본 `/media`)는 `compose.local.yaml` 에 있다 - 개발서버 `compose.yaml` 이 이 파일을
  포함하므로 서버 env 를 고치지 않아도 된다. 볼륨은 백업 대상이다(지우면 확정한 사진이 다시 확정해야 돌아온다).

## 관리자 화면 (`/admin/photo-review`)

시안 v51 그대로: 왼쪽 메뉴 '사진 검토'(검토 대기 수), 위 '시군 사진 / 정책 사진' 전환과 상태 보기, 가운데
자동 후보 · 이름으로 찾기 · 찾은 사진, 오른쪽 미리보기(지역 = 홈 시군 카드, 정책 = 상세 머리)와 결정 버튼.
결정하면 다음 검토 대기로 넘어간다.

## 시험

- 백엔드: 마이그레이션 SQL(`alembic upgrade 0046_photo_criteria:head --sql`, downgrade), 서비스(확정 → 응답에 사진,
  모두 아님 → 지역은 사진 없음 · 정책은 시군 사진, 다시 고르기, 결정된 대상은 수집이 안 건드림, 겹침 금지,
  검색이 음식점·숙박 · 다른 도를 뺌), 라우트(관리자만, 404, 503), autoflush 끈 세션.
- 프론트: 관리자 화면(목록 · 고르기 · 확정 뒤 다음 대상 · 단위 전환 · 찾기), 타입 검사, 빌드.
- 4173: 로컬 DB 에 0046·0047 을 올리고 관광공사 키로 수집을 돌려 후보를 채운 뒤 사용자 확인.

## 남는 위험

- 배포 직후 홈 시군 카드와 정책 상세 머리가 모두 혜택 그림이 된다(사용자 결정). 시군을 확정하는 만큼 돌아온다.
- 검토 양: 시군·도 약 70곳 + 정책 약 100건.
- `more` · `search` 는 요청 안에서 사진 서버에 크기를 묻는다(후보마다 한 번) - 몇 초 걸릴 수 있다. 확정도 원본 한 장을 받는다.
- 사진 파일은 볼륨 `travelhunter-media` 에만 있다. 볼륨을 지우면 확정 사진의 파일이 없어진다(화면은 그림이 깨지면 혜택 그림으로
  돌아간다). '다시 고르기' 뒤 다시 확정하면 파일이 없는 걸 보고 원본을 다시 받는다.
