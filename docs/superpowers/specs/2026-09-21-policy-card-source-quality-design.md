# 정책 수집원별 추출과 카드 표시 품질 설계

상태: 사용자 확정 요구사항을 정리한 설계. 구현 전 계획과 함께 검토한다.
기준: 2026-09-21, 로컬 develop `5eb23ec`. 구현 착수 시 최신 origin/develop에서 재확인한다.

## 목적과 확정한 정책

공식 원문의 혜택 의미·단위·조건을 유지하면서 사용자가 카드에서 혜택을 빠르게 이해하게 한다. 사용자는 불확실한 신규 정책을 관리자 승인 전까지 공개하지 않는 방식을 선택했다. 재수집한 변경 내용이 검토 중이면 기존 공개 정책은 마지막 승인 내용을 유지한다. 시간 경과에 따른 마감 처리는 계속 적용한다.

## 조사 근거와 한계

- 개발 DB 읽기 전용 조회에서 전국 범위 행은 traffic_benefit 11건, island_visit 1건이었다. active 필터 없는 DB 행 집계이므로 현재 화면 노출 건수와 같다고 주장하지 않는다.
- 교통 정책 benefit_detail에 `할인혜택 보러가기`, 기관 주소·저작권까지 포함한 178자 문구가 있었다. 11개 교통 행의 end_date는 모두 NULL이었다.
- 항공 정책 제목은 최대 4만 포인트인데 benefit_detail은 최대 1만 포인트였다. 원문의 지급 단위와 왕복·인원별 상한 관계를 함께 해석해야 한다.
- `travelmonth_traffic_parser.py`는 h4마다 새 레코드를 시작하고 p 텍스트를 수집한다. 마지막 정책 본문 종료 경계가 없고 같은 캠페인의 홍보 요약도 별도 정책이 될 수 있다.
- `policy_normalization.py:269,335`는 짧은 혜택 추출 실패 시 benefit_text 전체를 benefit_detail로 사용한다.
- `cards.tsx`와 `HomePage.tsx`는 policy.amount를 그대로 표시한다. `policy_semantics.py`도 benefit_detail을 우선한다.
- `policy_candidate_review.evidence_fingerprint`는 benefit_value_text·카드 추출 결과를 포함하지 않는다. 표현 수정만으로는 검토 후보가 갱신되지 않을 수 있다.
- 실제 사이트 DOM 변경에 대한 재현 fixture는 구현 Task 2에서 저장·검증한다. 이번 조사만으로 특정 DOM selector가 영구적으로 유효하다고 가정하지 않는다.

공식 근거(2026-09-21 확인):
- https://korean.visitkorea.or.kr/travelmonth/benefits/traffic.do — 예약·이용 기간, 포인트·운임쿠폰·렌터카 조건표가 혼재한다.
- https://korean.visitkorea.or.kr/travelmonth/benefits/stay.do?tab=2 — 할인액이 숙박 금액·박수·지역 조건에 종속된다.
- https://korean.visitkorea.or.kr/dgtourcard/biz/svcIntro/svcIntro.do — 주민증 발급과 가맹점별 혜택 이용 구조다.
- 섬은 저장소의 기존 `island_visit_promotion2_2026-09-14.html`과 신청 가이드 계약을 회귀 기준으로 삼는다. 이번 조사에서 최신 섬 웹 본문을 다시 검증했다고 주장하지 않는다.

## 공통 제약

- 수집 원문과 공식 URL을 보존하고, 카드 표시를 위해 원문을 덮어쓰지 않는다.
- 신규 의존성과 LLM 호출을 추가하지 않는다.
- 정책 id/slug와 사용자 찜·일정 링크를 변경하지 않는다.
- 공개 Policy DTO 필드는 유지하고, 관리자 후보 DTO만 확장한다.
- DB 스키마 변경 없이 기존 raw_payload·review_reason·benefit_detail을 활용한다.
- 운영·개발 DB의 재수집·일괄 갱신은 구현 검증과 분리하여 별도 실행한다.
- 검토 대기 중에는 마지막 승인 내용을 유지하고 기존 마감 처리를 적용한다.
- 비밀값을 출력하거나 커밋하지 않는다.

## 구성과 책임

1. 수집원별 파서는 정책 본문 경계를 잡고 혜택·대상·기간·조건·링크를 구분한다. HTML 수집 단계와 의미 추출 단계를 분리하되 기존 파서를 확장한다.
2. 작은 공통 카드 품질 모듈은 짧은 혜택 텍스트와 근거·문제 목록을 반환한다. 원문 전체를 요약 필드의 fallback으로 사용하지 않는다.
3. 원문 및 출처는 기존 ExternalSourceRecord에 남는다. 새 추출 결과는 raw_payload.cardCopy에 저장한다. 승인 시 검증된 summary만 Policy.benefit_detail로 복사한다.
4. 후보 생성·자동 공개 판정은 카드 품질을 포함한다. 기존 자동화 조건에 품질 조건을 추가하며 신규 정책의 수동 검토 원칙은 유지한다.
5. 관리자에게 원문, 실제 카드 표시 예정 문구, 근거, 보류 사유를 보여준다. 수동 승인도 안전한 동일 문구를 게시한다.

## 수집원별 의미 규칙

| 수집원 | 추출 단위 | 카드 표현 원칙 |
|---|---|---|
| 교통 | 실제 혜택/신청 단위. 반복 홍보 블록 제외 | 원·포인트·쿠폰·할인율 구분. 최대치의 인원/왕복 조건 보존 |
| 숙박 | 기존 캠페인과 지역 연결 구조 유지 | `최대 7만원 할인`에 필요한 박수/금액 조건은 상세에서 보존 |
| 반값여행 | 지자체별 지원 공고 | 환급률·한도·지역화폐/현금 차이를 유지 |
| 관광주민증 | 참여 지역 프로그램 | 가맹점별로 다른 혜택을 하나의 임의 할인율로 만들지 않음 |
| 섬 | 신청 차수와 대상 섬 카탈로그 | 기존 applicationGuide 및 서류 기한 유지. 지급 조건은 상세로 |
| 지역 혜택 | 목록 항목과 연결된 상세/modal | 제목·기간·할인 내용 라벨을 구분. 지역 미확정을 전국으로 추측하지 않음 |

카드 summary는 공백 정리 후 40자 이내를 품질 기준으로 제안한다. 넘으면 의미를 잘라 승인하지 않고 검토 사유로 남긴다. `무료 입장`처럼 숫자 없는 유효한 혜택도 허용한다. 버튼 문구, footer, script, 순수 항목명은 불허한다. 제목은 공식 명칭을 유지하며 이번 범위에서 일괄 개명하지 않는다.

## 검토와 공개

품질 사유: benefit_missing, benefit_not_summary, benefit_navigation_text, benefit_site_chrome, benefit_unit_ambiguous, period_ambiguous. 기간이 없다는 사실만으로 상시 정책을 부정하지 않는다. 명시된 기간이 충돌하거나 해석 실패한 경우 period_ambiguous다.

카드 문제가 있으면 자동 공개를 보류한다. 수동 승인 시 표시 가능한 summary가 없으면 `혜택 상세 확인`이라는 중립 문구를 게시한다. 관리자가 보는 미리보기와 공개 결과는 같아야 한다. 이 방식은 승인 자체가 추출되지 않은 금액을 만들어내지 않게 한다. 이번 범위에 후보 문구 편집기를 추가하지 않는다. 정확한 수동 문구 입력이 필요하면 기존 관리자 정책 편집/override 흐름을 사용한다.

선택 승인·전체 승인 기능은 유지한다. 확인 문구에 품질 보류 후보 포함 가능성과 중립 문구 게시를 알린다. 서버에서 같은 안전 투영을 적용해 클라이언트 제한만으로 보호하지 않는다. 후보가 수집 중 바뀌면 이전 후보 승인은 409로 처리한다.

## 기존 데이터와 호환성

기존 공개 정책은 자동 정정/삭제하지 않는다. 새 코드 배포만으로 기존 amount를 교체하지 않으며, 수정된 추출 결과를 후보로 제시하고 승인 후 바꾼다. 사라진 홍보 레코드를 수집 결과에서 제외해도 기존 게시 행의 자동 삭제로 이어지지 않는다. 기존 교통 canonical_key가 문구를 포함하므로 승인된 행과 연결할 수 없는 경우 병합/신규 생성 작업을 멈추고 충돌 목록을 보고한다. 영구 ID 설계와 기존 중복 링크 병합은 별도 범위다.

기존 승인 정책을 보여주는 API가 최신 ExternalSourceRecord를 읽어 amount·조건을 재계산하면 승인 경계를 우회한다. 정상 Policy 경로는 승인된 Policy 값만 사용한다. raw fallback 경로는 기존 허용 수집원과 노출 조건을 유지하면서 안전한 카드 투영을 사용한다.

## 검증과 출시 기준

고정 HTML fixture, 순수 품질 단위 테스트, 후보 승인/배치/자동화 통합 테스트, PostgreSQL 경쟁 테스트, 관리자 UI 테스트를 사용한다. 기존 상세·홈·일정·찜의 승인 내용 유지와 마감 회귀를 확인한다. 마지막으로 격리 스택에서 수집→검토→승인→카드 표시를 검증한다. 라이브 사이트 결과 건수를 테스트 기대값으로 고정하지 않는다.

구현은 함께 작성한 계획 검토 후 시작한다. 기존 2026-09-16 text-quality 및 2026-09-18 card-copy 계획의 원문 fallback 제거/카드 문구 항목은 이 설계와 새 계획을 우선한다. 이전 문서는 삭제하지 않으며 이미 구현된 레이아웃 작업을 다시 수행하지 않는다.
