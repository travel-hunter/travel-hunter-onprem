# 카카오 장소값 저장 제거와 공공데이터 장소 설계

상태: 사용자 확정 설계(2026-10-03). 단계별 구현 계획을 승인받은 뒤 착수한다.
기준: 2026-10-03, origin/develop `1817f67`. 통합 검색 PR(`feature/unified-search`, 푸시 전)의 변경을 함께 다룬다.

## 목적과 확정한 정책

일정에 담은 장소가 카카오 로컬 API 응답값에 기대지 않게 한다. 사용자는 공공데이터로 우리 장소 기반을 만드는 방식(A안)을 골랐다.

- 카카오 로컬 API 응답의 장소명·주소·좌표·전화번호는 DB·로그·주소(URL)에 남기지 않는다.
- 장소 검색과 화면 표시는 지금처럼 카카오를 실시간으로 쓴다.
- 일정에 저장하는 장소는 우리 데이터만 쓴다. 공공데이터 장소(TourAPI, 소상공인 상가정보)이거나 사용자가 직접 정한 값(이름, 지도에서 찍은 위치)이다.
- 카카오는 장소 ID와 `place_url`만 저장해 '카카오맵에서 보기' 링크로 쓴다.
- 카카오 값을 외부로 보내지 않는다. 공공 API 질의도 포함한다. 공공데이터를 우리 DB에 받아 두고 서버 안에서 비교한 뒤 버린다.
- 카카오 결과로 다른 회사 지도 링크를 만들지 않는다.

## 현재 상태

저장은 모두 `backend/app/repositories/trips.py`의 `add_trip_place`를 거친다. 카카오가 준 `place_name`·`address`·`latitude`·`longitude`·분류를 그대로 넣는다.

| 들어오는 길 | 코드 | `source_provider` |
|---|---|---|
| 추천 장소 카드 | `services/trips.py` `list_recommendations` → `services/itinerary_recommendations.py` `additional_place_candidates`. 서버가 '{시군} 맛집' 같은 말로 카카오를 검색해 카드(최대 18개)를 만든다 | `kakao_local` |
| 일정 안 장소 검색 | `services/trips.py` `search_places_for_trip` → 장소 추가·일괄 추가·수정 | `kakao` |
| 홈 '일정에 담기'(통합 검색 PR) | `frontend/src/utils/placeHandoff.ts` → 위 추가 경로 | `kakao` |

- 2026-10-03 읽기 전용 집계로 운영 252건(일정 16개), 개발서버 439건(일정 25개, 중복 제외 366곳)이 저장돼 있다.
- 통합 검색 PR은 홈 `pl`·`addPlace`, 정책 탭 `near` 주소에 카카오 장소의 이름·주소·좌표를 싣는다. Caddy가 쿼리를 지워 서버 로그에는 남지 않는다. 하지만 브라우저 기록과 공유 링크에는 남는다.
- `backend/app/core/debug_capture.py`를 일정 장소 경로에 켜면 요청 본문(카카오 값)이 로그에 남는다. 항상 빼는 경로는 인증·초대뿐이다.
- 일정 장소를 편집하면 이름·메타(분류·주소)가 브라우저 `localStorage` 초안에 남는다(`frontend/src/pages/itinerary/ItineraryDetailPage.tsx` `saveDraft<TripPlaceEditDraft>`, 키 `trip-place:{일정}:edit:{장소}`). 카카오에서 온 장소를 편집하면 카카오 값이 남는다.
- 백업에도 남는다. 운영 #54 전환(2026-08-30)의 개발 원본 덤프 `dev-full-20260830-1824.dump`가 개발서버와 운영 서버에 한 벌씩 있었다(운영 서버 사본은 644). 2026-10-03에 두 벌 모두 지웠다. 지금 운영의 카카오 장소 252건은 모두 이 스냅샷에서 넘어왔다(전부 이전 전에 만든 일정). 같은 전환의 옛 운영 DB(`travelhunter_before_20260830_1824`)와 그 덤프(`prod-before-20260830-1824.dump`)에는 일정이 없었다. 작업 전에 손으로 뜬 개발서버·로컬 DB 덤프도 있다(3절 '백업과 보존').
- 문제없음: 통합 검색 API(`/api/places/*`)는 저장·캐시 없이 전달만 한다. 카카오 검색 로그는 검색어와 건수만 남긴다. 일정 장소를 LLM으로 보내는 코드도 없다.

## 실측

개발서버 저장분 366곳을 공공데이터와 비교했다. 카카오 값은 비교 프로세스 메모리에만 두고 버렸다.

- 공공데이터: TourAPI 국문 6개 유형 47,656건(관광지·문화시설·레포츠·쇼핑·숙박·음식점, 2026-10-03)과 소상공인 상가정보 20260630판 2,772,484건이다.
- 반경: 관광명소·문화시설 1km, 나머지 200m. '같음'은 띄어쓰기·기호를 뺀 이름이 같은 것, '포함'은 한쪽 이름이 다른 쪽에 들어 있는 것이다.

| 분류 | 장소 | TourAPI 같음 | 상가정보 같음 | 둘 중 하나 같음 | 같음+포함 |
|---|---|---|---|---|---|
| 관광명소 | 109 | 59% | 2% | 60% | 80% |
| 음식점 | 120 | 38% | 70% | 78% | 90% |
| 카페 | 78 | 21% | 51% | 57% | 82% |
| 숙박 | 51 | 39% | 15% | 50% | 58% |
| 합계(기타 포함) | 366 | 40% | 37% | 63% | 80% |

- 같음으로 맞은 TourAPI 장소 149곳 중 121곳에 사진이 있다.
- TourAPI 실시간 반경 조회(`locationBasedList2`)는 같은 200m에서 훨씬 적게 돌려줬다(전체 12%). 받아 두고 비교하는 근거다.
- 한계: '포함'에는 다른 장소가 섞인다(예: '오동도'와 '오동도 등대'). 표본은 개발 데이터다.

## 설계

### 1. 데이터

새 표 `public_places`가 우리 장소 기반이다.

- 행: TourAPI 6개 유형 전체와 상가정보 대분류 음식·숙박·예술·스포츠(약 104만 건), 합쳐 약 108만 행이다. 소매·교육·부동산 같은 업종은 넣지 않는다.
- 열: 출처(`tourapi`·`sangga`), 출처 ID(`contentid`·상가업소번호), 이름, 비교용 이름, 도로명주소, 위도·경도, 분류, 시도·시군, 사진 URL·저작권 유형(TourAPI만), 갱신일.
- 색인: (출처, 출처 ID) 고유, 위도·경도 범위 조회, 비교용 이름.
- 크기: 수백 MB로 본다. 서버 DB는 지금 12~16MB이고 디스크 여유는 900GB 이상이다. 백업 파일과 로컬 시험 DB 동기화가 그만큼 커진다.
- 갱신: TourAPI는 주 1회 동기화한다(약 50회 호출). 실행 방식은 기존 정책 수집 스케줄러를 따르며 2단계 계획에서 정한다. 상가정보는 분기 파일을 받아 적재한다. 서버 적재는 실행할 때마다 승인받는다.

`trip_places`는 저장하는 값을 바꾼다.

- 열을 나눠 출처를 잃지 않게 한다.
  - `place_origin`: `public`(공공데이터 장소), `custom`(나만의 장소), `needs_review`(변환 후 확인 필요)
  - `public_source`(`tourapi`·`sangga`)와 `public_source_id`
  - `photo_url`·`photo_license`(TourAPI만)
  - 카카오 장소 ID와 링크는 기존 `external_place_id`·`place_url`에 두고, `source_provider`는 `kakao`로만 쓴다.
- 공공데이터 장소는 그 장소의 이름·주소·좌표·분류·사진을 저장하고 출처·출처 ID를 남긴다. 외래키로 묶지 않는다. 공공데이터가 갱신되거나 지워져도 일정은 담을 때 값을 유지한다.
- 나만의 장소는 사용자가 쓴 이름과 사용자가 지도에서 찍은 좌표만 저장한다. 찍지 않으면 좌표를 비운다. 주소와 분류는 비운다.
- 카카오 장소 ID와 `place_url`은 모든 경우 '카카오맵에서 보기'용으로 저장한다.
- 스키마는 Alembic `0048`로 바꾼다. nullable 열을 더하기만 하므로 앞 버전 코드도 그대로 돈다.
- `debug_capture`는 장소 경로(`/api/places/*`, 일정 장소 추가·수정)를 설정과 무관하게 항상 뺀다. 2단계에서 `ALWAYS_EXCLUDED_MARKERS`에 `place`를 더하고 시험한다.

### 2. 장소를 담는 흐름

일정 안 장소 추가 창과 3단계 이후의 홈 '일정에 담기'에 같이 쓴다.

1. 검색과 결과 목록은 지금처럼 카카오 실시간이다.
2. 사용자가 장소를 고르면 프론트가 그 항목(카카오 ID, 이름, 좌표, 분류)을 맞춰 보기 API(`POST /api/places/match`, 로그인 필요)로 보낸다. 서버는 `public_places`에서 분류별 반경(관광명소·문화시설 1km, 나머지 200m) 안의 후보를 찾아 비교용 이름을 견준다. 받은 값은 저장하거나 로그에 남기지 않는다.
3. 결과는 세 갈래다.

| 경우 | 화면 | 저장 |
|---|---|---|
| 이름이 같은 공공데이터 장소(실측 약 63%) | 바로 바구니에 담는다 | 공공데이터 이름·주소·좌표·사진 + 카카오 ID·링크 |
| 이름 일부만 겹치는 후보(약 17%) | 공공데이터 후보 1~3개로 '이 장소가 맞나요?'를 묻는다 | 고르면 위와 같다. '아니요'면 아래와 같다 |
| 맞는 게 없음(약 20%) | '나만의 장소' 칸이다. 빈 이름 칸과 [지도에서 위치 찍기](선택)가 있다 | 사용자가 쓴 이름 + 찍은 위치 + 카카오 ID·링크 |

- 바로 담는 것은 반경 안에 이름이 같은 공공데이터 장소가 **하나뿐일 때**만이다. 둘 이상이면 후보 확인으로 보낸다.
- 나만의 장소에서는 카카오 이름을 미리 채우지도, 옆에 참고로 보여 주지도 않는다.
- 편집 초안(`localStorage`)에는 공공데이터 값과 사용자 입력만 들어간다. 구형 행(`kakao`·`kakao_local`)은 편집을 열면 확인 화면(이름 다시 쓰기)으로 바뀌고, 카카오 이름을 초안에 넣지 않는다.
- 위치 찍기 지도는 일정 지역에서 시작한다. 카카오 좌표에 맞춰 열지 않는다. 사용자가 누른 점이 사실상 카카오 좌표가 되는 우회를 막기 위해서다.
- 장소 추가 API는 공공데이터 장소 참조나 나만의 장소 값(이름, 선택 좌표)을 받는다. 서버는 공공데이터 값을 클라이언트에서 받지 않고 자기 표에서 채운다.
- 이미 담은 장소의 이름을 사용자가 고치면 사용자 입력으로 저장한다.
- 추천 장소 카드는 카카오 검색 대신 `public_places`에서 일정 지역·분류로 고른다. TourAPI 장소(사진 있는 곳 먼저)를 먼저 보이고, 모자라면 상가정보로 채운다.
- 일정 화면 표시:
  - 공공데이터 장소는 이름·주소·핀·사진(공공누리 출처 표시)과 카카오맵 링크를 보인다.
  - 나만의 장소는 사용자 이름과 카카오맵 링크를 보이고, 핀은 찍은 경우만 보인다.
  - '확인 필요'는 '장소 이름을 다시 적어 주세요'와 카카오맵 링크, 겹치는 공공데이터 후보를 보인다.
- 화면은 구현 전에 시안으로 먼저 확인한다.

### 3. 기존 저장분 변환

1. 일정 장소 표를 백업한다. 덤프는 권한 600으로 저장소 밖에 둔다.
2. 변환을 미리 실행해 건수만 센다.
   - 이름이 같은 공공데이터 장소가 반경 안에 하나뿐이면 그 값으로 바꾸고 `public`으로 표시한다.
   - 나머지(없음, 둘 이상)는 카카오 이름·주소·좌표·분류를 지우고 카카오 ID·링크만 남긴 채 `needs_review`로 표시한다.
   - 행마다 지문(행 ID, 이름, 주소, 좌표, 분류의 해시)을 남긴다.
3. 적용할 때 지문이 미리 실행 때와 다른 행(그사이 사용자가 고친 행)은 건너뛰고, 그 행만 다시 미리 실행한다.
4. 카카오에서 온 값이 남지 않았는지 센다.
5. 승인받고 적용한다. 개발서버를 먼저 하고 운영을 뒤에 한다.
6. 브라우저의 예전 편집 초안을 무효화한다. 초안 키의 판을 올려 예전 초안은 읽지 않고, 앱이 시작할 때 예전 판 키를 지운다.

운영 예상은 252건 중 약 160건 변환, 약 90건 확인 필요다. 같은 이름이 둘 이상인 경우는 확인 필요로 가므로 실제 변환 건수는 이보다 조금 적다. `place_name`은 NOT NULL이므로 확인 필요 행에는 이름 대신 정해진 안내 문구를 넣는다. 화면은 `place_origin`으로 이를 구분한다.

### 4. 통합 검색 PR 변경

- 홈 장소 카드의 '일정에 담기' 버튼을 3단계 전까지 숨긴다. 검색, 장소 카드, '이 근처', 카카오맵 링크는 그대로 둔다.
- 홈 `pl`·`from`과 정책 탭·홈 `near`에는 카카오 장소 ID와 사용자가 친 검색어만 싣는다.
- 장소 값은 화면 메모리에서 꺼낸다. 메모리는 앱을 쓰는 동안 최근 200곳을 30분까지 두고, 새로 고침과 로그아웃 때 비운다.
- 메모리에 없으면 같은 검색어로 다시 검색해 같은 ID의 장소를 그린다. 홈은 기존 검색 요청 하나로 찾는다. 찾지 못하면 홈은 검색 결과로, 정책 탭은 `near`를 지운 그 시군 화면으로 돌아간다.
- 메모리 캐시가 운영정책 5조 20호의 '사용자 환경 개선 목적의 캐시'에 드는지는 운영자 확인이 필요한 해석으로 남긴다.
- 일정 쪽 `?addPlace` 받기는 3단계에서 새 흐름에 맞춰 바꾼다.

## 배포 순서

PR은 늘 develop 대상이다. 앞 PR이 머지된 뒤 다음 PR을 연다.

1. 통합 검색 PR: 4절의 변경이다. **노출을 줄이는 단계일 뿐 저장 문제의 해결이 아니다.** 일정 안 장소 검색, 추천 카드, `?addPlace` 받기는 여전히 카카오 값을 저장한다. PR 본문과 CHECKLIST에 그렇게 적는다.
2. 우리 장소 기반: `public_places`, TourAPI 동기화, 상가정보 적재 스크립트, 맞춰 보기 API, `debug_capture` 제외. 화면 변화는 없다.
3. 담는 흐름: 2절의 세 갈래 흐름, 나만의 장소, 추천 카드, API 계약 변경. 시안부터 만든다.
   - 저장은 새 방식으로만 한다. 카카오 이름·좌표를 받아 저장하던 경로를 없앤다.
   - 구형 행(`kakao`·`kakao_local`)은 그대로 읽어 보여 준다.
   - '확인 필요' 화면을 이 단계에서 함께 낸다. 구형 행을 편집하면 그 화면이 열린다.
4. 기존 저장분 변환: 확인 화면이 나간 뒤에 데이터를 바꾼다. 변환 스크립트, 예전 초안 무효화, 백업 처리를 한다.

되돌리기는 단계마다 다르다.
- 2·3단계는 앞 버전을 다시 배포한다. `0048`은 열을 더하기만 한다.
- 4단계는 되돌리지 않는 것을 원칙으로 한다. 문제가 있으면 변환 규칙을 고쳐 다시 돌리고, 백업 복원은 보존 기간 안에서만 한다.

운영은 지금 `0035`에 멈춰 있고, 나중에 최신 develop으로 맞출 예정이다. 2~4단계를 운영에 적용하는 것은 그 배포 뒤다. 그 배포가 #54 안정화 기간의 끝이기도 하다(3절 '백업과 보존').

서버 작업(공공데이터 적재, 변환, 덤프 정리)은 개발서버와 운영 각각 실행할 때마다 승인받는다.

## 계약과 시험

- 일정 장소 API(`POST /trips/{trip_id}/days/{day_number}/places`, `.../places/batch`, `PATCH /trips/{trip_id}/places/{place_id}`, `GET /trips/{trip_id}/recommendations`)의 요청·응답과 새 맞춰 보기 API를 `docs/mvp-api-contract.md`, 프론트 타입, 백엔드 스키마, `.agent/evals`에 함께 반영한다.
- 맞춰 보기 규칙(정규화, 분류별 반경, 같음·포함)을 단위 시험으로 고정한다.
- 장소 추가 후 DB 행에 카카오 이름·주소·좌표가 없는지, 맞춰 보기 요청 본문이 로그에 남지 않는지 시험한다.
- 변환 스크립트는 미리 실행 결과를 고정한 시험 데이터로 확인한다.
- 담는 세 갈래와 나만의 장소를 화면 시험과 e2e로 확인한다.

## 위험과 미정

- '포함' 후보는 다른 장소일 수 있어 사용자 확인에 맡긴다.
- 추천 카드의 맛집 품질이 떨어질 수 있다. 공공데이터에는 순위와 평점이 없다.
- 나만의 장소에서 이름을 다시 쓰는 불편이 약 20%에 생긴다.
- 상가정보는 분기 갱신이라 새로 연 가게가 늦게 들어온다.
- TourAPI 개발계정은 하루 1,000건이다. 운영은 활용사례 등록 후 늘릴 수 있다.
- 일정에 보이는 이름이 공공데이터 표기로 바뀔 수 있다(예: 상호명과 지점명이 나뉜 체인점).
- 운영자 답변의 해석은 바뀔 수 있다. 우리 사례(일정에 담은 장소 저장)로 데브톡에 확인받는 것은 선택 사항이다.
- 범위 밖: 공공데이터 장소의 네이버 지도 링크, 나만의 장소를 검토해 우리 장소 기반에 넣는 등록 흐름.
