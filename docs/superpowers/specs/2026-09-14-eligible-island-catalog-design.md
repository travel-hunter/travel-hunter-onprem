# 섬 방문의 해 대상 섬 카탈로그 설계

## 목적

`섬 방문의 해` 여행비 지원은 정책 카드 한 건으로 유지한다. 공식 공지에 첨부되는 지역별 Excel 대상 섬 목록은 정책 본문이나 정책 카드 목록으로 풀지 않고, 일정 추천에만 쓰는 별도 **대상 섬 카탈로그**로 관리한다.

공식 공지 또는 첨부 파일이 바뀌면 수집기가 변경 후보를 만들고, 관리자가 내용을 확인해 승인한 경우에만 현재 카탈로그를 바꾼다. 승인 전 변경은 공개 정책 카드와 일정 추천 결과에 영향을 주지 않는다.

## 검증된 현재 경계

- 현 `PolicyReviewCandidate`는 `external_source_records.id`를 필수 외래키로 사용하고, 승인 시 외부 레코드를 정책으로 승격한다. 따라서 섬 목록 후보를 여기에 넣으면 정책 카드 게시와 대상지 목록 갱신이 같은 승인 의미를 갖게 된다.
- 현 `TripPlace`에는 `place_name`, `address`, 좌표가 있으며, 섬 식별자는 없다. 첫 버전의 추천은 장소 이름의 정규화된 완전 일치만 사용할 수 있다.
- 현 `island_visit` 수집기는 `promotion2`에서 여행비 지원 정책 한 건을 만들고 `eligibleIslandsUrl`만 원시 데이터에 남긴다. 목록을 파싱하거나 추천에 사용하는 경로는 없다.
- 현 백엔드 의존성에는 `.xlsx`를 읽는 `openpyxl` 또는 동등 라이브러리가 없다. 실제 첨부 목록을 읽는 구현에는 지원 라이브러리와 고정된 테스트 픽스처가 필요하다.

## 범위와 비범위

### 포함

- 공식 공지의 Excel 첨부 목록을 감지·다운로드·검증해 대상 섬 카탈로그 변경 후보를 생성한다.
- 관리자가 추가·삭제·변경 개수와 출처를 보고 승인 또는 거절한다.
- 승인된 대상 섬만 일정의 장소 이름과 정확히 일치할 때 섬 여행비 지원 정책을 추천한다.
- 정책 상세에는 승인된 대상 섬 총수와 공식 안내 링크만 보인다.

### 제외

- 섬 하나당 정책 카드 생성
- 유사어·부분 문자열·시군구만으로 하는 추천
- 승인 없이 공개 목록이나 추천 결과를 자동 변경하는 처리
- 섬 이외 정책의 수집 구조 변경
- 이용자에게 "대상 섬이 아님"을 안내하는 판정

## 데이터 모델

정책 수집 모델과 별도의 다음 모델을 둔다. 모든 DB 필드는 `snake_case`, API DTO는 `camelCase`를 사용한다.

1. `eligible_island_catalogs`
   - 프로그램 식별자(`island_visit_2026`), 표시 이름, 공식 공지 목록 URL, 활성 상태를 보관한다.
   - 현재 승인 스냅샷을 가리키는 참조를 둔다. 승인 처리에서 이 행을 잠가 동시 승인을 직렬화한다.

2. `eligible_island_catalog_snapshots`
   - 한 번의 공지 수집으로 만들어진 후보 버전이다.
   - 공지 URL·제목·첨부 파일 URL·파일명·정렬된 첨부 SHA-256 지문·파서 버전·수집 시각·총 대상지 수·상태(`pending`, `approved`, `rejected`, `superseded`)를 보관한다.
   - 이전 승인본과 비교한 추가·삭제·변경 수를 보관한다.

3. `eligible_island_snapshot_entries`
   - 스냅샷 안의 원본/정규화 대상지다.
   - `display_name`, `normalized_name`, `jurisdiction_name`, 원본 행의 지역 정보와 행 지문을 보관한다.
   - 동일 관할·동일 정규화 이름은 중복 제거하고, 이름이 같아도 관할이 다르면 별도 대상지로 보존한다.

4. `eligible_islands`
   - 현재 승인된 읽기 전용 카탈로그다.
   - 승인 시 한 트랜잭션에서 현재 행을 새 승인 스냅샷의 행으로 교체한다. 추천과 정책 상세는 이 테이블만 읽는다.

첨부 파일 자체는 저장하지 않는다. 출처 URL·파일명·SHA-256과 파싱 결과만 보관한다. 원본 보관이 필요해지면 별도 객체 저장소 정책을 먼저 정한다.

## 수집 및 검토 흐름

```text
공식 공지 목록
  -> 최신 대상 섬 공지/첨부 링크 탐색
  -> 첨부 파일 다운로드
  -> SHA-256 비교
  -> 동일 지문: 파싱·DB 쓰기 없이 종료
  -> 새 지문: Excel 형식 검증 및 파싱
  -> 안전 게이트 통과: pending 스냅샷 + 항목 diff 생성
  -> 관리자 승인: approved 카탈로그 원자 교체
  -> 정책 상세 수치/일정 추천에 반영
```

공지 목록에 지역별 파일이 여러 개면, 각 파일 지문을 정렬해 하나의 집합 지문으로 만든다. 파일 한 개만 바뀌어도 새 스냅샷을 만든다. 동일 집합 지문이면 내려받은 파일을 다시 파싱하거나 현재 승인 목록을 갱신하지 않는다.

관리자 화면은 일반 `정책 검토 후보`와 분리된 `대상 섬 목록 갱신 후보` 탭이다. 후보에는 총수, 추가/삭제/변경 수, 공지 제목·URL, 첨부 파일명·URL, 수집 시각, 안전 경고를 표시한다. 승인과 거절은 스냅샷 단위이며, 한 섬씩 승인하지 않는다.

## Excel 파서와 실패 안전성

- `.xlsx`는 `openpyxl`로 읽는다. `.xls`, ZIP이 아닌 파일, 암호화 파일, 다운로드 HTML은 지원하지 않고 `parser_changed` 또는 `download_failed`로 기록한다.
- 헤더에서 최소한 섬 이름과 관할 지역을 식별할 수 있어야 한다. 알려진 동의 헤더만 허용하고, 필수 열이 없으면 현재 승인 카탈로그를 절대 변경하지 않는다.
- 공백 정리와 Unicode NFC만 이름 정규화에 사용한다. `도` 제거, 접미어 제거, 부분 문자열 매칭 등 의미를 바꾸는 정규화는 하지 않는다.
- 파싱 결과가 0건이면 후보를 만들지 않고 실패로 기록한다.
- 이전 승인본보다 30%를 초과해 줄어들면 자동 후보 생성은 중단하고 `suspicious_shrink` 경고를 남긴다. 관리자는 출처를 확인한 뒤 별도 강제 수집 절차를 통해서만 새 후보를 만들 수 있다.
- 더 새 수집 결과가 있으면 기존 `pending` 스냅샷은 `superseded`로 바꾼다. 거절된 스냅샷도 현재 승인 목록을 변경하지 않는다.

## 정책 카드와 일정 추천

`island_visit` 정책 카드의 기존 수집 텍스트·제목·혜택 문구는 바꾸지 않는다. 정책 상세에만 다음의 파생 정보가 추가된다.

- `eligibleIslandCount`: 승인된 `eligible_islands` 수
- `eligibleIslandsOfficialUrl`: 공지 또는 대상 섬 공식 안내 URL

일정 추천에서는 해당 정책만 별도 조건을 적용한다.

1. 정책이 공개 가능하고 마감되지 않았는지 기존 조건을 통과한다.
2. 일정의 `TripPlace.place_name`을 NFC·공백 규칙으로 정규화한다.
3. 승인 카탈로그의 `normalized_name`과 완전 일치하는 장소가 하나 이상일 때만 섬 정책을 후보에 넣는다.
4. 일치하지 않으면 조용히 후보에서 제외한다. 사용자에게 비대상이라는 부정 판정은 제공하지 않는다.

이 규칙은 현재 `TripPlace`에 공식 섬 코드가 없다는 한계를 의도적으로 보수적으로 다룬다. 예를 들어 `거문도 선착장`과 `거문도`는 첫 버전에서 일치하지 않는다. 별칭·지오코딩 기반 확대는 정확도 근거를 갖춘 후속 작업이다.

## API와 화면 경계

- 관리자 전용: 카탈로그 수집 실행, pending 스냅샷 목록/상세/diff, 승인, 거절 API.
- 일반 정책 API: 위의 두 파생 읽기 필드만 추가한다. 전체 대상 섬 목록은 일반 정책 카드 응답에 싣지 않는다.
- 일정 API: 추천 응답의 기존 모양을 유지한다. 섬 정책이 조건을 만족하면 기존 추천 항목으로 나타난다.
- 프런트엔드는 `AppDataApi` 경계만 통해 위 API를 사용한다.

## 테스트 및 검증 기준

1. 정상 지역별 `.xlsx` 픽스처를 파싱해 기대한 섬·관할·집합 지문을 만든다.
2. 동일 첨부 지문이면 두 번째 수집이 파싱과 DB 변경을 하지 않는다.
3. 필수 열 누락, 잘못된 파일, 다운로드 실패, 0건 결과, 30% 초과 감소가 현재 승인 카탈로그를 보존한다.
4. 스냅샷 diff의 추가·삭제·변경 수와 관할별 중복 규칙을 검증한다.
5. 승인 전에는 정책 상세 수치와 일정 추천이 기존 승인본 그대로임을 검증한다.
6. 승인 시에만 카탈로그가 원자적으로 교체되고, 오래된 pending 후보는 승인할 수 없음을 검증한다.
7. 장소 이름 완전 일치만 섬 정책을 추천하며 부분/별칭/같은 시도만의 일치는 추천하지 않음을 검증한다.
8. 관리자 권한·API 계약·프런트 화면 테스트, migration SQL 검토, 관련 backend/frontend 전체 게이트를 실행한다.

## 첫 운영 절차

1. 배포 전 DB 백업과 기존 정책·일정 링크 건수를 기록한다.
2. migration 적용 후 관리자가 공지 수집을 한 번 실행한다.
3. 후보의 총 대상지 수와 지역별 파일 수를 공식 공지와 대조한다. 기대와 다르면 승인하지 않는다.
4. 승인 후 정책 상세의 대상 섬 수와 정확 일치 일정 하나·불일치 일정 하나를 확인한다.
5. 승인 전후 정책 카드의 기존 수집 텍스트가 동일한지 확인한다.

## 결정 기록

이 설계는 대상 섬 목록을 정책 카드 수집의 `raw_payload`에 묻지 않는다. 목록은 사용자 추천에 영향을 주는 별도 도메인 데이터이며, 데이터 형식 변경·대량 삭제·승인 이력이 필요한 수명 주기가 정책 카드와 다르기 때문이다.
